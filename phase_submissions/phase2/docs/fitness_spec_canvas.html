Multi-Agent System Specification Canvas

95864 · Agentic Technologies · Phase 2
Constraint-Aware Fitness Planner — specification canvas for system intent, roles, control boundaries, shared state, internal tools, and evaluation
1 System Intent
1
🎯 System Mission
Help users create realistic, non-clinical diet and workout plans that reflect multiple real-world constraints such as food intolerances, symptom triggers, limited time, limited equipment, budget constraints, and adherence difficulties. The primary user is a constrained fitness-planning user; the operational secondary stakeholder is a trainer, dietitian, or referring healthcare provider who may inspect the plan summary, warnings, and unresolved risks. Multi-agent coordination is justified because the system must do more than generate recommendations: it must structure user input, detect conflicts, decide when to clarify or stop, review the plausibility of the plan, and revise it later after user feedback while preserving prior context.
2
👥 Agent Roster & Profiles
AgentsThe same four-agent structure from Phase 1 is preserved: Intake & Profile Builder structures input; Constraint & Risk Checker detects conflicts and safe-scope violations; Plan Composer drafts the plan; Review & Adaptation Agent audits and revises; Human supplies missing data, resolves tradeoffs, and reports execution feedback.
ProfilingAll roles are designer-defined and intentionally narrow. Their responsibilities are separated so the workflow remains auditable and each handoff produces an inspectable artifact.
JustifySeparation prevents the system from jumping directly from messy input to final plan. Intake handles structure, Constraint Checker handles safety and conflict detection, Plan Composer handles constructive output, and Review Agent handles reflection and adaptation.
3
🔲 System Scope & Boundaries
In scopeConstraint-aware non-clinical planning, goal-constraint conflict detection, clarification questions, realistic weekly structure, review-driven revision, and adaptation after adherence failure.
Why MAThe problem requires specialized workflow decisions, not just one-shot content generation. Multi-role design supports bounded autonomy, visible escalation, and stateful revision.
Out scopeDiagnosis, treatment advice, medication advice, disease interpretation, automatic calorie estimation from images, and any claim that the system replaces licensed professionals.
2 Multi-Agent Structure
4
🏗️ Social & Organizational Structure
PatternCentralized orchestration with role-based handoffs. A single workflow controller routes the session through intake, checking, composition, review, and adaptation.
Human roleThe human is not passive. They act as the resolution authority for missing data, conflicting priorities, and acceptance of the final plan.
Why fitA centralized structure keeps stopping conditions, permissions, and traceability legible, which is important for a health-adjacent bounded system.
5
🔗 Communication Structure & Protocol
ArtifactsEach handoff uses a structured artifact: profile object, constraint report, plan package, review notes, feedback event, and revised plan version.
RoutingClarification loop returns to the human; unresolved hard conflict routes to human prioritization; clinical boundary routes to stop; review failures route back to Plan Composer.
ProtocolThe prototype uses deterministic JSON-like state updates rather than free-form inter-agent chat, improving comparability across evaluation cases.
6
🖥️ Environment & Interface Structure
PrototypeA browser-based HTML/CSS/JavaScript prototype provides intake, branching, visible workflow logs, and versioned session state. This makes the process inspectable for Phase 2.
ToolsThe prototype uses an internal tool layer: intake form, missing-field detector, conflict checker, medical boundary checker, plan template library, review heuristic, and state/log renderer. These tools are enough to specify how each role acts without requiring external services.
GroundingThe current prototype is grounded in user-provided profile data plus internal rules and templates. No web retrieval or external document corpus is required for the bounded Phase 2 workflow.
3 Multi-Agent Behavior & Control
7
⚙️ Individual Behavior Specification
IntakeSchema-filling and missing-field detection. Asks follow-up questions when profile completeness is inadequate.
CheckerRule-based gating for hard constraints, ambiguity, and medical boundary detection.
ComposerTemplate-guided planning that maps recommendations to user goal, schedule, equipment, and restrictions.
ReviewReflection-style critique and revision focused on adherence realism, hidden conflict detection, and change explanation.
8
🤝 Collective & Social Behavior
CollectiveThe system behaves cooperatively rather than competitively. Each role narrows uncertainty or improves output quality before the next stage proceeds.
FeedbackUser feedback creates the main adaptive loop: real-world execution results cause targeted plan revision instead of unrelated regeneration.
BDI-liteBeliefs are captured in the shared profile and constraint report; desires are the user goal and safety requirements; intentions are the currently approved plan version and revision commitments.
9
🛑 Operating Rules, Norms & Human Checkpoints
MustRespect stated restrictions, ask for clarification under ambiguity, preserve hard constraints during revision, and explain major recommendations.
Must notDiagnose, recommend medication, interpret disease, or overclaim certainty from incomplete data.
HumanThe user confirms profile details, resolves tradeoffs, accepts or rejects the final plan, and provides execution feedback for adaptation.
10
🔄 Cross-Domain Feedback Topology
ForwardUser input → profile structuring → conflict/risk analysis → plan drafting → review → reviewed output.
ReverseExecution feedback → Review & Adaptation Agent → targeted revision of meal structure, session duration, or scheduling.
StopsBoundary stop for clinical requests; pause for missing information; human prioritization for unresolved tradeoffs.
4 Context & Evaluation
11
🧾 System I/O & Shared State
InputsGoal, restrictions, symptom triggers, schedule, equipment, adherence concerns, budget, user notes, and later execution feedback.
OutputsProfile object, clarification prompt, constraint report, plan package, review notes, revised plan, and boundary warnings.
MemoryShort-term session memory only. The prototype keeps versioned state during the current interaction. It intentionally does not use long-term persistent memory in Phase 2 because privacy burden and correction cost outweigh the current continuity need.
12
🚨 System Failure Modes & Escalation
FailuresMissed hard constraints, false confidence under ambiguity, overly difficult plans, clinical overreach, and tradeoff denial.
EscalateClinical requests stop immediately. Missing or vague information triggers clarification. Conflicting hard constraints trigger human prioritization. Review failures trigger revision.
TraceEach branch and stop condition is visible in the prototype log and reflected in versioned state for later evaluation.
13
🌫️ Scenario & Uncertainty Management
AmbiguityThe system treats ambiguous symptom-trigger descriptions as an information gap rather than as permission to infer a medical interpretation.
No RAGRAG is intentionally excluded in Phase 2 because the prototype is not trying to answer document-grounded factual questions. The central challenge is user-specific coordination under constraints, not retrieval quality.
Tool boundaryNo external action tools are used in Phase 2. The system does not contact APIs, message other people, or operate outside the prototype environment. This keeps permissions narrow and behavior auditable.
14
✅ System Success Criteria
TaskAll hard constraints satisfied in each test case.
ProcessClarification occurs before planning when required; medical boundary requests are stopped; review can revise a weak first draft; unresolved tradeoffs route to the human.
QualityAt least one soft adherence preference is reflected, major recommendations include rationale, and revision preserves prior hard constraints.
EvidenceTraces, case-based evaluation files, failure logs, version notes, and reviewer-facing canvases make the workflow auditable for Phase 2 and reusable in Phase 3.
