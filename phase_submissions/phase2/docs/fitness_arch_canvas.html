1 Agent Design & Reasoning
1
🧠 Agent Model Strategy
Per rolePhase 2 prototype uses deterministic JavaScript modules rather than live LLM calls. This is intentional: the core claim being tested is workflow logic, not model scaling. If upgraded later, Intake, Plan Composer, and Review Agent could share one general-purpose model while Constraint Checker remains rule-based.
Why fitThe current task is bounded, explainable, and testable without a live model. This keeps the prototype right-sized and prevents unnecessary complexity. The four-role structure from Phase 1 is preserved, but the control logic is now more explicit and testable.
ProfilesRole identities are designer-defined through explicit functions and responsibilities rather than stochastic prompting, which improves repeatability during evaluation.
2
⚙️ Individual Behavior Implementation
CognitiveIntake uses schema-filling and missing-field checks. Constraint Checker uses rule-based routing. Plan Composer uses template-based planning. Review Agent uses reflection-style critique and revision. This combines staged planning with explicit review rather than relying on one-pass generation.
ToolsThe system does use tools, but they are internal workflow tools rather than external APIs: structured intake form, missing-field detector, conflict rule engine, medical boundary checker, plan template library, review heuristics, and trace/state logger.
TemporalThe workflow is event-driven. Each user submission or feedback event advances the system through clarification, planning, review, or adaptation stages.
3
⏱️ Temporal Dynamics & Simulation Model
Time modelEvent-driven interaction model rather than fixed time steps. A run begins with initial input, may loop through clarification, then progresses to checking, composition, review, and output. A later user feedback event reopens the revision loop.
PhasesPhase order is explicit: intake → constraint/risk check → plan compose → review → output → optional adaptation. Review is allowed to send the plan backward one stage for revision.
StopThe workflow stops when the user accepts the reviewed plan, when clarification is not provided, or when a clinical boundary is triggered.
2 Structure Implementation
4
🏛️ Orchestration & Organizational Architecture
OrchestratorCentralized state-machine controller implemented in JavaScript. This controller routes between roles based on explicit conditions rather than hidden prompt logic.
Why centralA centralized architecture makes handoffs, permissions, and stopping conditions easy to inspect. It also makes escalation paths explicit: clarification returns to the human, unresolved tradeoffs route to prioritization, clinical boundary requests stop, and weak drafts are revised before approval.
ControlThe orchestrator supervises transitions, stores state, and prevents later modules from bypassing earlier safety or completeness checks.
5
📡 Communication Infrastructure
FormatStructured objects for profile, constraint report, plan package, review notes, feedback log, and plan version history.
RoutingClarification messages go to the human; review messages go to the Plan Composer; adaptation messages update the current plan version; boundary warnings terminate the chain.
TraceabilityEach state transition is exposed in the UI log, giving a lightweight trace for evaluation and later screenshot capture.
6
🧰 Environment & Grounding Infrastructure
Internal toolsStructured intake form, missing-field detector, conflict rule engine, medical boundary checker, plan template library, review heuristics, and trace logger. These are the concrete tool interfaces used by the roles in Phase 2.
External toolsNot used in Phase 2. The prototype does not call web APIs, databases, messaging systems, or external action tools because the current goal is to test control logic rather than backend integration.
RAGNot used in Phase 2. Retrieval is unnecessary because the system is not solving a document-grounded citation task. The main problem is coordinated reasoning over the user's bounded profile and revision history.
7
💻 Scale & Computational Architecture
RuntimeSingle-page browser application with no backend dependency for the prototype build.
BenefitLow-latency, easy to inspect, simple to demonstrate in class, and cheap to iterate on.
Trade-offLimited external grounding and no persistent data storage, which is acceptable for Phase 2 because the submission emphasizes architecture and testability over production deployment.
3 Collective Behavior & Quality
8
🤝 Coordination Strategy & Mechanism
MechanismSequential specialization with centralized routing. Coordination is cooperative, not adversarial: each role contributes a bounded transformation of the state.
TheoryBDI-lite framing: beliefs = profile and constraints; desires = user goal plus safety policy; intentions = currently approved plan and revision commitments.
Why fitThis keeps the system easier to follow than debate-based or decentralized patterns, which would add complexity without solving the main failure modes here.
9
🧭 Emergent Behavior Detection & Steering
UndesiredUnsafe overreach, hidden conflict, optimistic planning, and plan drift away from hard constraints are the main failure patterns to detect and suppress.
SteeringExplicit rules, review-stage critique, and human prioritization keep the workflow from silently drifting into unsupported or unsafe behavior.
ObservabilityLogs and versioned state expose the process so that reviewers can inspect why a branch, stop, or revision occurred instead of seeing only final output.
10
🧪 Verification & Conflict Resolution
VerifyConstraint Checker validates feasibility before planning. Review Agent validates realism and scope after planning. Both stages can block release.
ResolveUnresolved hard conflicts are not auto-decided; they are surfaced to the human for prioritization.
JudgePhase 2 relies on manual review plus scenario-based checks. Phase 3 can extend this with code-based evaluators and rubric-style judges.
11
📏 Calibration & Validation Protocol
CasesSix scenario-based test cases cover baseline planning, ambiguity, hard conflict, medical boundary stop, revision after failure, and false-confidence resistance.
MetricsHard constraint satisfaction, clarification trigger, boundary compliance, adherence-fit, revision coherence, and explicit uncertainty handling.
LensProcess-oriented evaluation is emphasized over outcome alone. The goal is not only to inspect whether a plan looks plausible, but also to verify whether clarification, stopping, prioritization, and revision occurred at the right stage.
4 State, Planning & Trade-Offs
12
🗂️ State Management & Feedback Architecture
Short-termUsed. Session memory stores profile, missing fields, constraint report, plan versions, review notes, and feedback log during the active interaction.
Long-termNot used. Persistent cross-session memory is excluded in Phase 2 because privacy risk, correction burden, and governance overhead are not justified by the current prototype scope.
FeedbackUser execution feedback updates only the affected plan elements while preserving stable hard constraints and prior decisions.
13
🪜 Task Decomposition & Planning
StagesIntake → check → compose → review → output → adapt. Structured intermediate stages are easier to inspect, revise, and evaluate than one-pass generation, especially in a safety-bounded planning workflow.
BranchesClarification branch, clinical stop branch, human prioritization branch, and review-driven revision branch.
ReasonThese stages map directly to the main failure modes of the project: incomplete input, hidden conflict, medical overreach, weak first drafts, and revision after real-world failure.
14
⚖️ Trade-Off Priorities
Priority 1Safety and bounded autonomy. The system must stop for diagnosis and medication requests rather than trying to be maximally helpful.
Priority 2Constraint fidelity. Hard restrictions and feasibility conditions matter more than producing a detailed or ambitious plan.
Priority 3Adherence realism. A slightly simpler plan that the user can follow is better than a theoretically optimal but brittle plan.
Priority 4Low complexity. No long-term memory, no RAG, and no live external tools are added unless they solve a real Phase 2 failure mode. This preserves clarity for the rubric rather than adding decorative technical complexity.
